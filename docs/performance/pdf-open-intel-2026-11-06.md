# Intel Mac PDF 打开与滚动空白优化（2026-11-06）

在 Intel MacBook Pro 上用真实文库副本测量当前生产构建的冷启动打开速度和滚动表现，定位瓶颈后修改后台位图管线，再按同一方法复测。基线是 `a296d20`（已包含此前的页面虚拟化、后台绘制、文字分批等优化）。

结论：这台机器上滚动时主线程本身不卡（基线 P95 帧回调间隔约 17.5 ms，无 long task），用户看到的“卡”主要是**页面来不及绘制而显示空白**，以及打开时首页出现慢。修改后，打开到首页可见缩短 25–60%，普通论文和图片较多的论文在快速滚动时的空白基本消失。翻译稿中矢量图极重的页面仍然跟不上滚动，见“未解决”。

## 环境和方法

- MacBookPro15,1，Intel Core i7-9750H，16 GB RAM，macOS 15.8.1，Retina DPR 2；Electron 44.9.3 / Chromium 152。Chromium 使用独立显卡 AMD Radeon Pro 555X（`force_high_performance_gpu` 生效），Intel UHD 630 空闲。
- 生产构建，1400 × 860 可见、有焦点的窗口。测试期间同机另有一个 Freddie 实例占用浏览器剪藏端口，对所有轮次相同。
- 每一轮是一个新的应用进程，启动后直接打开指定文献（与重新启动应用后继续阅读相同），因此主进程位图缓存为空、后台 worker 为冷启动。每个场景 3 轮，下表取中位数。
- 打开：从 renderer 导航开始，到视口中第一页有完成的位图（首页可见），以及视口内所有页面都有位图（视口绘制完成）。
- 滚动：打开完成后静置 1.5 s，用 CDP 原生鼠标滚动手势滚动 6000 CSS px，速度 1500 px/s 和 4000 px/s 各一次。每 16 ms 检查一次两个阅读栏视口内的页面：“空白采样”为视口内存在未绘制页面的采样比例，“空白面积”为未绘制部分占视口页面面积的比例。帧间隔为主线程 `requestAnimationFrame` 回调间隔，不是显示器最终呈现帧率。
- 文档（均来自用户文库的副本）：

| 文档 | 模式 | 特点 |
| --- | --- | --- |
| DeepSeek-R1 | 单栏 | 86 页，普通论文 |
| Symbian OS Internals | 单栏 | 940 页扫描书，无文字层 |
| MinerU2.5-Pro | 单栏 | 43 页，19 MB，图片多 |
| GLM-5 | 双栏 | 原文 40 页 + 44 MB BabelDOC 译文，矢量图重 |
| MAI-Thinking-1 | 双栏 | 从第 7 页开始，译文页文字片段密集 |

## 瓶颈

1. **位图串行生成**：主进程只有一个绘制 worker，renderer 队列一次只请求一页，两个阅读栏共用。双栏打开时顺序为原文 p0、p1，然后才是译文 p0、p1；一页重的图表会挡住两个栏的所有后续页面。
2. **PNG 编码比绘制本身还贵**：在 worker 中单独计时（DPR 2，约 1.9 MP 每页）：

| 步骤 | 普通页面 | 重矢量页面（GLM-5 第 3 页） |
| --- | ---: | ---: |
| PDF.js 绘制 | 30–60 ms | 5.3–5.5 s |
| PNG 编码 | 100–120 ms | 约 100 ms |
| `getImageData` 读取原始像素 | 1–4 ms | 1–4 ms |

   renderer 收到 PNG 后还要再解码一次。
3. **worker 首页慢**：新 worker 绘制第一页时 V8 尚未编译 PDF.js 的解析和绘制代码。同一进程先画一页内置小 PDF，DeepSeek-R1 首页从 429 ms 降到 104 ms，MinerU 从 887 ms 降到 586 ms。
4. GLM-5 译文的畸形字体让 PDF.js 每个字形输出一条警告，测试中约 10 万行写入主进程 stdout。

## 修改

- **原始像素代替 PNG**：worker 用 `getImageData` 取得非预乘 RGBA，前置 8 字节宽高（`electron/main/pdfRasterFormat.ts`），不再编码、解码 PNG。主进程内存缓存上限由 64 MiB 调整为 96 MiB（仍最多 64 项），以容纳未压缩位图。
- **两个绘制 worker**：请求优先交给已解析该文档的空闲 worker，只在全部忙时启用第二个。双栏中一栏的重页面不再挡住另一栏。renderer 位图队列同时允许两个请求；浏览器回退绘制改由独立的串行锁保证一次一页，与原来相同。
- **renderer 侧接收移出主线程**：专用 Web Worker 读取约 7.7 MB 的像素数据并生成 `ImageBitmap`，主线程只用 `bitmaprenderer` 的 `transferFromImageBitmap` 显示，不再复制；该 worker 不可用时在原线程完成。
- **启动预热**：两个绘制 worker 随主窗口启动，导入 PDF.js 后先绘制一页内置 PDF（`electron/main/pdfRasterWarmup.ts`，含标准字体文字、填充与描边路径和一张图片）。
- worker 中 PDF.js 日志级别设为只输出错误。

渲染器权限、协议路径校验、PDF 字节、批注、同步格式均未改变。

## 结果（中位数，3 轮）

| 文档 | 指标 | 基线 | 修改后 |
| --- | --- | ---: | ---: |
| DeepSeek-R1 | 首页可见 | 1007 ms | 606 ms |
|  | 4000 px/s 空白采样 / 面积 | 12.9% / 1.3% | 0% / 0% |
| Symbian（940 页） | 视口绘制完成 | 1124 ms | 586 ms |
|  | 1500、4000 px/s 空白 | 0% | 0% |
| MinerU | 首页可见 | 1589 ms | 1202 ms |
|  | 1500 px/s 空白采样 / 面积 | 21.8% / 14.1% | 16.6% / 10.6% |
|  | 4000 px/s 空白采样 / 面积 | 35.9% / 13.1% | 6.7% / 2.0% |
| GLM-5（双栏） | 首页可见 / 视口绘制完成 | 1486 / 3480 ms | 850 / 2289 ms |
|  | 1500 px/s 空白采样 / 面积 | 90.7% / 79.9% | 90.4% / 81.6% |
|  | 4000 px/s 空白采样 / 面积 | 89.2% / 73.0% | 54.7% / 31.0% |
| MAI-Thinking-1（双栏） | 首页可见 / 视口绘制完成 | 1610 / 2144 ms | 647 / 1489 ms |
|  | 4000 px/s 空白采样 / 面积 | 34.9% / 4.9% | 4.9% / 0.6% |

所有场景修改后 P95 帧回调间隔为 17.5–18.7 ms，与基线一致，均无 long task。MAI-Thinking-1 在 1500 px/s 下两版都有一次约 83 ms 的峰值；GLM-5 在 4000 px/s 下两版都有约 33 ms 的峰值。1500 px/s 滚动中单个位图请求的中位耗时（含排队）在其他四个场景从 85–169 ms 降到 43–94 ms；GLM-5 例外，从 150 ms 升到 672 ms。可能是两个 worker 在同一时间内完成了更多重图表页，使完成请求中重页面的比例升高，未单独验证。

双栏场景的数据来自一个中间版本：renderer 队列以 `PdfRenderQueue(2, 0)` 构建，当时代码还带一个“为可见页保留一个位置”的参数。保留数为 0 时它的调度与最终的 `PdfRenderQueue(2)` 完全相同。单栏场景使用最终源码，源码哈希记录在 JSON 中。

### 已撤回的尝试：为可见页保留一个位置

曾限制预取页面最多占用一个位置，想让后打开的译文栏可见页不被原文预取挡住。对照测量（同样 3 轮）显示打开时间没有变化（GLM-5 视口绘制完成 2306 vs 2289 ms），快速滚动反而更差（GLM-5 4000 px/s 空白面积 53.1% vs 31.0%，MAI-Thinking-1 空白采样 7.2% vs 4.9%），因此已删除。

## 未解决

- **重矢量页面**：GLM-5 原文和译文第 3 页单页绘制约 5.5 s，其他图表页 0.4–1.5 s，绘制量本身超过滚动速度，1500 px/s 下仍有约 90% 的采样存在空白。曾有两轮因故障实际走了浏览器回退绘制（见下），其中 GLM-5 在 1500 px/s 下 2/3 轮几乎没有空白，但主线程帧间隔变差。这提示 Chromium 画布可能比 worker 中的原生画布更适合这类页面，例如在 renderer 的 Worker 中用 OffscreenCanvas 绘制；尚未验证。
- MinerU 的图片页单页仍需数百毫秒，1500 px/s 下约 17% 的采样有空白。
- 资源代价：应用启动时即启动两个 worker 并各自绘制一页预热，即使不打开 PDF；每页位图跨进程传输约 7.7 MB（DPR 2），主进程缓存上限 96 MiB。
- 只测了这一台 Intel Mac 和独立显卡；未覆盖缩放、手写、后台翻译并发负载、Apple Silicon 和其他操作系统。

## 排除的数据

前两轮修改后的测量全部作废：worker 从 `pdfRasterWorkerClient.ts` 导入常量，构建把该模块拆成共享 chunk，其中按 `__dirname` 拼出的 worker 路径指向 `out/main/chunks/`，worker 无法启动，所有位图请求返回 404，阅读器实际在测浏览器回退绘制。单元测试用 esbuild 单独打包 worker，没有覆盖这一点。已改为独立的 `pdfRasterFormat.ts`，测试脚本现在遇到任何非 200 的位图响应即判该轮失败。

## 功能验证

- 类型检查、全量测试（438 通过、1 跳过）和生产构建通过。新增测试覆盖原始像素格式、双 worker 并行与文档亲和、预热 PDF 无需修复即可解析、渲染队列并发、回退绘制串行和损坏的位图数据。
- 在这台机器上让位图请求全部返回 503，确认浏览器回退绘制仍能正常显示（MAI-Thinking-1 单轮：视口绘制完成 1223 ms，滚动无空白，P95 32.5 ms）。
- 测试使用临时文库副本，没有修改源文库，也没有替换已安装的应用。

逐轮数据、打开阶段每个位图请求的时间、机器信息和源码哈希保存在 [实测 JSON](./pdf-open-intel-2026-11-06.json)。

## 复测

在有图形会话的 macOS 上，在仓库根目录运行（脚本会先构建生产版本）：

```sh
FREDDIE_BENCH_PAPERS=fcfdbda7-f407-462b-925f-31d49737e7a4:pdf,b7c585c4-9f7d-490a-a4a8-5ad38a1d901b:pdf,5b3e077a-dff1-4781-8893-a54ebe392165:pdf,edb20d05-5008-457f-a165-2c3bcd356b5c:bilingualPDF,c67552c1-38c9-4aa4-88af-3c7803a79366:bilingualPDF:6 \
FREDDIE_BENCH_TRIALS=3 \
node scripts/benchmark-pdf-open.mjs
```

每项格式为 `文献 UUID:模式[:起始页索引]`。默认读取 `~/Library/Application Support/Freddie`，可用 `FREDDIE_BENCH_LIBRARY` 指定；`FREDDIE_BENCH_SPEEDS`、`FREDDIE_BENCH_DISTANCE` 控制滚动，`FREDDIE_BENCH_NO_WORKER=1` 测量浏览器回退绘制。脚本只测当前源码，不构建基线；对比基线需先检出对应提交再运行一次。
